\section{Validation Procedure and Consistency Argument}
\label{app:proofs}
Algorithm~\ref{alg:validate} states the observation and validation protocol of \S\ref{sec:design} for one source.

\begin{algorithm}[ht]
\caption{Consistent observation or validation of one source}
\label{alg:validate}
\small
\begin{algorithmic}[1]
\Require explicit adapter contract; old certificate for validation
\If{contract missing, unsupported, or old schema incompatible}
 \State \Return \Unknown
\EndIf
\For{$i=1,2,3$}
 \State $E_0\gets$ complete provider evidence
 \State $Q\gets$ query snapshot; collect support and complete change evidence
 \State $E_1\gets$ complete provider evidence
 \If{same epoch and evidence, with all contract guards satisfied}
  \State bind $Q$ to this attempt's certificate
  \State \Return observed value, or comparison with old value
 \EndIf
\EndFor
\State \Return \Unknown
\end{algorithmic}
\end{algorithm}

For Proposition~\ref{thm:sound}, consider a successful attempt. In the atomic case, the provider transaction returns the value and metadata from one snapshot. In the bracket case, the adapter's complete, non-repeating evidence is equal at both boundaries, within the same provider epoch. Under the proposition's premises, no relevant committed mutation occurs between those boundaries. All query, support and change reads are inside them, so their combined evidence describes the same relevant state. Comparing with a preceding certified value is therefore sound at the inner query snapshot. A retry discards every read of the unsuccessful attempt. Exhaustion, missing evidence and epoch mismatch return \Unknown. The result does not cross sources or extend beyond the certified interval.

For Observation~\ref{thm:indist}, take an execution with no relevant write and an execution with one committed write whose notification has not yet been delivered. Before delivery, the stipulated reader sees identical prior state, lifecycle observations and delivered events. It therefore makes the same decision in both executions, although the source values differ. A fixed wait changes this argument only if an additional premise excludes writes during the relevant interval and establishes delivery completion.

\paragraph{Concrete reference guards.} In the reference, the evidence is the pair (database epoch, monotone sequence); every provider call returns it with the rows and an in-transaction timestamp from one SQLite transaction. An attempt takes five such snapshots (before, query, support, delta, after) and certifies the query snapshot when the before and after pairs are equal; the client does not compare the inner pairs or timestamps. The independent oracle recomputes every verdict from the logs and checks that each stable attempt's five snapshots share the pair and have ordered timestamps, and that the certificate equals the query rows. Unsupported stock contracts return \Unknown before any snapshot is read.

\paragraph{Minimal contract for joined queries.} A provider can make a joined query certifiable with four additions, each with a matching client guard:
\begin{enumerate}[nosep,leftmargin=*]
\item a provider-wide sequence that every commit to any table the query joins advances, returned in the same transaction as the rows; the client certifies only if the sequence is equal before and after its reads;
\item a reset-safe epoch that a wipe, restore or migration rotates; any epoch change returns \Unknown and forces a full refresh;
\item delete tombstones kept at least as long as the client may be absent, or an explicit signal that history was truncated; a truncation returns \Unknown;
\item membership changes, rows entering or leaving the query's predicate, that advance the sequence like any other commit, so that equal sequences also mean equal membership.
\end{enumerate}
Our one-row reference meets these by construction (\S\ref{sec:design}); no stock provider we tested exposes the first two.

\paragraph{iOS.} iOS gives readers what Android lacks for Contacts and Photos. A Contacts change-history request returns add, update and delete events since an opaque token~\cite{apple_cnchangehistory}, and a drop-everything event tells the reader that incremental history is no longer possible~\cite{apple_cndropeverything}; Photos returns persistent changes since a change token~\cite{apple_phpersistent} and fails with an expired-token error when the token is older than the kept history~\cite{apple_phtokenexpired}. These give deletions and an explicit restart signal, which play the roles of items 3 and 2 above, but not item 1: the history and the value are separate reads. On iOS the decision table would therefore swap the candidate stamp for the history token, treat a drop-everything event or an expired token as an epoch break, and still bracket the value read by two tokens before certifying. We did not measure iOS.

\paragraph{Conditional effects today.} Contacts writes can already be conditional: a batch that asserts the row's \texttt{VERSION} before updating fails with an \texttt{OperationApplicationException} when the row changed~\cite{android_cpo}, which the client reports as \Unknown and answers by re-reading. Calls, messages and shares cannot: placing a call takes an address, not a contact row and version~\cite{android_telecom}, a message takes a destination address, and a share hands the receiver a content URI that it reads after the check. The closest a client gets is to re-validate just before the effect, pass the certified value itself (the number, or a copied file instead of a live URI), and on a mismatch stop and ask the user, which narrows but does not close the check-to-effect window measured in \S\ref{sec:eval-boundary}. Effect-if-version would let the system reject the call, message or share with an explicit stale-source error when the row no longer has the certified version.
